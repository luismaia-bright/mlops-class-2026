# Class 2 — Infrastructure as Code for MLOps
Bright Version
You will stand up a complete MLOps stack from a single file, train a bonsai species
classifier inside it, register the best version, promote it, and watch a serving API pick
up that promotion without being touched.

The point of the class is not the classifier. It is that **every piece of the environment
is a file in this repository**, so anyone can recreate it exactly, months later, on a
different machine.

## What you need

- Docker and Docker Compose
- A browser

That is the whole list. No Python, no MLflow, no conda on your machine.

## Quick start

```bash
git clone https://github.com/luismrmaia-dev/mlops-class-2026.git
cd mlops-class-2026/aula2_mlop_infra/docker
docker compose up -d --build
```

The first run builds two images and takes a few minutes. Then open:

| Service | URL | What it is |
|---|---|---|
| JupyterLab | http://localhost:8888 | Your workspace — open `work/bonsai_classifier.ipynb` |
| MLflow | http://localhost:5001 | Experiment tracking and model registry |
| API | http://localhost:8080 | Model serving |

> **Why MLflow is on 5001 and not 5000** — macOS binds port 5000 to the AirPlay Receiver.
> Inside the containers MLflow still listens on 5000; `docker-compose.yml` publishes it on
> 5001. Getting this wrong is the single most common way to lose the first ten minutes of
> a class.

## What is in here

```
aula2_mlop_infra/
├── api/app.py                      # Serves models:/Bonsai-Species-Classifier@champion
├── docker/
│   ├── docker-compose.yml          # The whole stack
│   ├── Dockerfile                  # API image
│   ├── Dockerfile.jupyter          # JupyterLab image, pinned
│   ├── requirements.txt            # API dependencies, pinned
│   ├── requirements-notebook.txt   # Notebook dependencies, pinned
│   └── init-mlflow.sh              # MLflow server startup
├── notebooks/bonsai_classifier.ipynb
└── README.md
```

Two directories appear once you run things and are **deliberately not in git**:

- `db/` — the MLflow SQLite database
- `artifacts/` — logged models, plots and datasets

This is worth a minute in class. Models do not belong in git: they are large, binary, and
already versioned somewhere better. The registry is the system of record for models; git
is the system of record for code. Confusing the two is how repositories end up at 4GB.

## The classifier

Four measurements in, one of four species out:

| Input | Unit |
|---|---|
| `leaf_length_cm` | cm |
| `leaf_width_cm` | cm |
| `branch_thickness_mm` | mm |
| `height_cm` | cm |

| Id | Species | Care |
|---|---|---|
| 0 | Juniper | Full sun, minimal watering, wire training in fall |
| 1 | Ficus | Bright indirect light, consistent moisture, frequent pruning |
| 2 | Pine | Full sun, well-draining soil, candle pinching in spring |
| 3 | Maple | Partial shade, consistent moisture, shelter from wind |

> The training data is **synthetic**, generated by `sklearn.make_classification`. Whatever
> accuracy we report describes the generator, not bonsai biology. Treat the numbers as a
> vehicle for the MLOps mechanics.

## Promotion, and why there are no stages here

MLflow used to promote models through fixed stages (`Staging`, `Production`). Those are
deprecated. We use **aliases** instead: `@candidate` marks a version to be tested,
`@champion` marks the version being served.

The API loads `models:/Bonsai-Species-Classifier@champion`. Moving that alias *is* the
deployment — and moving it back *is* the rollback.

## Troubleshooting

**Check everything at once**

```bash
docker compose ps
docker compose logs --tail=50
docker stats --no-stream
```

**MLflow UI will not load** — remember it is on **5001**, not 5000.

```bash
docker compose logs mlflow
docker compose exec jupyter curl -s http://mlflow:5000/health
```

**JupyterLab asks for a token** — it should not; the compose file disables it. If you
changed the command:

```bash
docker compose logs jupyter | grep -i token
```

**API returns 503** — this is expected before you have promoted anything. It means no
version carries the `@champion` alias yet. Run the promotion cell in the notebook, then:

```bash
curl -s http://localhost:8080/
curl -X POST http://localhost:8080/reload
```

**API still serves the old model after a promotion** — it caches the model after first
load. Tell it to pick up the new champion:

```bash
curl -X POST http://localhost:8080/reload
```

**Test a prediction end to end**

```bash
curl -X POST http://localhost:8080/predict \
  -H "Content-Type: application/json" \
  -d '{"features": [2.1, 1.8, 5.5, 25.3]}'
```

On Windows, use PowerShell for the JSON body:

```powershell
Invoke-RestMethod -Uri http://localhost:8080/predict -Method Post `
  -ContentType 'application/json' -Body '{"features":[2.1,1.8,5.5,25.3]}'
```

**Port already in use** — something else is on 5001, 8080 or 8888. Find it:

```bash
ss -tlnp | grep -E '5001|8080|8888'     # Linux
netstat -ano | findstr "5001 8080 8888" # Windows
```

**Start over completely** — this deletes tracked runs and artifacts:

```bash
docker compose down -v
rm -rf ../db ../artifacts
docker compose up -d --build
```

## Not covered in this class

These get named in passing and are deliberately out of scope — there is no honest way to
teach any of them in the time we have:

- Blue-green and rolling deployments, rollback strategies beyond moving an alias
- Backup and disaster recovery for the tracking store
- Horizontal scaling, resource limits and tuning
- Container security hardening (this stack runs MLflow as root with `chmod 777` on its
  volumes — a shortcut that is called out in `docker-compose.yml` and would be
  unacceptable in production)
- Authentication on any of the three services
